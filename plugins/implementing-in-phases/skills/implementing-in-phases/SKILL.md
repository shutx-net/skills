# implementing-in-phases — Phased Implementation

実装タスクを「計画」と「実装」に分けるワークフロー。計画をフェーズごとのJSONファイルとして一時ディレクトリに書き出し、構造を機械的に検証してから、フェーズ単位で実装する。計画JSONはgitリポジトリには含めない。

## 役割

| 役割 | 担う作業 | effort（ユーザーに質問できない場合の既定値） |
| --- | --- | --- |
| 親（この会話） | effortの決定、計画の検証と確認、フェーズごとの結果確認、ユーザーとのやり取り、完了報告 | — |
| 計画担当 | 調査・設計・フェーズ分割、計画の見直し、原因の分析、重要な変更の最終レビュー | high |
| 実装担当 | 1フェーズ分の実装とテスト | medium |

- **サブエージェントを使う場合**: 計画担当と実装担当（1フェーズにつき1体）をサブエージェントとして起動する。モデルとeffortの指定方法は、次のホスト別ガイドに従う。親のモデルは変更しない。
- **サブエージェント機構が無い場合、またはユーザーが使用しないと指定した場合**: すべての役割を自分で順に担う。モデルは切り替えず、ホスト別ガイドも読まない。
- ユーザーが明示した指定（モデル・effort・進め方）と、ホスト側の強制設定や制限を優先する。指定どおりに適用されたと確認できない設定を、適用済みとして報告しない。
- サブエージェントの質問は親に戻し、親がユーザーに確認する。

## ホスト別の起動設定

サブエージェントを使う場合は、Step 0の前に実行環境に合うガイドを**1つだけ**読む。起動設定だけを確認する依頼では、ユーザーが設定対象として指定したホストを使う。モデル名、起動引数、再開方法はホスト別ガイドにまとめてある。

| ホスト | 読むガイド |
| --- | --- |
| Claude Code | `references/claude-code.md`（`LOAD references/claude-code.md`） |
| Codex | `references/codex.md`（`LOAD references/codex.md`） |

その他のホストでは、利用可能な起動ツールの仕様に従う。モデルを選べるなら計画担当には推論を重視したモデル、実装担当には通常のコーディング用モデルを使い、選べなければ親のモデルを継承する。モデルとeffortは対応する起動パラメータで渡し、存在しない引数は使わない。

各役割の手順はこのスキルの次のファイルにある。サブエージェントに任せるときは、内容を貼らずにパスを渡す。

| ファイル | 内容 |
| --- | --- |
| `references/planner.md` | 計画担当の手順（`LOAD references/planner.md`） |
| `references/implementer.md` | 実装担当の手順（`LOAD references/implementer.md`） |
| `references/plan-schema.md` | 計画・結果ファイルの形式と検証項目（`LOAD references/plan-schema.md`） |
| `scripts/validate_plan.py` | 計画と結果ファイルの検証スクリプト |

## ワークフロー

### Step 0: effortレベルの決定

ユーザーのプロンプトにeffortレベルの指定があるか確認する。

- **指定がある場合**: そのレベルを全役割に使う。「軽く・ざっくり」「徹底的に・入念に」等の度合いを表す表現も指定とみなしてよい。
- **指定がない場合**: **必ずユーザーに選択させる**（選択UIがあればそれを使い、なければ質問して回答を待つ）。勝手にデフォルトを決めない。選択肢は実行環境がサポートするeffortレベルを提示する。選ばれたレベルを全役割に使う。
- **ユーザーに質問できない場合**（サブエージェントとして起動された、非対話モードで実行されている等）に限り、役割の表の既定値を使い、そのことを完了報告に書く。

決めたeffortは、サブエージェントを起動するたびにホストのeffortパラメータで渡す（プロンプトに書くだけでは設定されない）。effortを指定する仕組みがないホストでは、起動プロンプトに書いて引き継ぐ。

### Step 1: 計画ディレクトリの用意

計画JSONは**gitリポジトリの外**に置く。リポジトリ内に作成してはならない。

- 環境が用意する作業用一時ディレクトリ（scratchpad等）があればその下、なければ `/tmp` の下に作る。例: `/tmp/implementing-in-phases/<YYYYMMDD-HHMMSS>/`
- `mkdir -p` で作成し、計画ディレクトリとリポジトリのルート（`repoRoot`）の絶対パスを控える。
- このスキルの `references/planner.md`・`references/implementer.md`・`references/plan-schema.md` を計画ディレクトリにコピーする。サブエージェントが読むファイルを1か所にまとめ、作業ディレクトリ外の読み取りを最小限にするため。
- 読み取り専用のモード等で書き込めない場合は、ユーザーにそのことを伝え、書き込める状態にしてもらう。

### Step 2: 計画立案

計画担当（サブエージェント1体、または自分）が `planner.md` に従って計画を書く。読み取り専用のエージェント種別は計画を保存できないため、ファイルを書き込める種別を使う。渡す情報:

- タスク内容（ユーザーの依頼の全文または忠実な要約）
- `repoRoot`、計画ディレクトリ、計画ディレクトリ内の `planner.md` と `plan-schema.md` の絶対パス
- effortレベル

計画担当はソースコードを変更しない。gitで管理されている場合、親は計画の前後で `git status --porcelain` の出力を比べ、作業ツリーが変わっていないことを確認する。

### Step 3: 計画の検証と確認

1. 検証スクリプトを実行する。このSKILL.mdがあるディレクトリを基準に `python3 scripts/validate_plan.py <計画ディレクトリ>`（Python 3 の標準ライブラリだけで動く）。
   - ERROR があれば、計画担当に修正させるか自分で直し、再実行する。ERROR が残っている計画では実装を始めない。
   - WARNING は内容を確認し、必要なら直す。
   - Python が使えない場合は、`plan-schema.md` の Validation の項目を自分で確認し、スクリプトを実行できなかったことを完了報告に書く。
2. `openQuestions` が残っていれば、ユーザーに確認する。回答を計画に反映して空にしてから再検証する。
3. ユーザーにフェーズ一覧（タイトル・目的・依存関係）を簡潔に提示する。
4. 計画に明らかな問題（タスクとの乖離、過剰な分割など）があれば、先へ進む前に修正する。

### Step 4: フェーズごとの実装

フェーズを `dependsOn` の依存関係順に進め、フェーズごとに次を繰り返す。

1. **実装担当に任せる**（1フェーズ = 1体。サブエージェントがなければ自分）。`implementer.md` に従わせる。渡す情報（計画や結果の全文はプロンプトに貼らない）:
   - 計画ディレクトリ内の `implementer.md`・`plan-schema.md`・`plan-index.json`・担当の `phase-NN.json`・依存先フェーズの `result-NN.json` の絶対パス
   - 書き出す `result-NN.json` のパスと、effortレベル
2. **結果を確認する**。
   - 検証スクリプトを再実行し、`result-NN.json` の形式も確認する。
   - 報告と実際の差分（`git status`・`git diff` 等）を照合し、報告にない変更や計画外の変更がないか確かめる。
3. **`status` に応じて判断する**。
   - `completed`: 次のフェーズへ進む。
   - `unverified`: 実行できなかった検証を親が実行できるか確かめる。できなければユーザーに伝え、進めるかどうかを決める。
   - `needs_replan`: 計画担当に影響を確認させ、関連するフェーズの計画を更新させる。再検証してから後続のフェーズへ進む。
   - `needs_user_decision`: ユーザーに確認する。
   - `blocked`: 環境の不足や権限エラーを切り分ける。モデルを変えるだけで解決しようとしない。
   - `failed`: 差分・再現手順・失敗ログ・試した内容を計画担当に渡して原因を分析させる。計画の更新が必要なら更新して再検証し、そのフェーズをやり直す。

依存が互いに独立なフェーズは、変更対象ファイルが重ならない場合に限り並行して進めてよい（重なりは検証スクリプトが WARNING で示す）。検証コマンドがビルド出力・データベース・ポート等を共有する場合は並行させない。

### Step 5: 全体の検証と完了報告

- 全フェーズの完了後、プロジェクトのテスト・リント等の全体検証を実行する。
- 公開API・データ移行・セキュリティに関わる変更など重要な変更は、必要に応じて計画担当と同じモデルにレビューさせる。
- 完了報告には以下を含める:
  - 実装したフェーズと変更ファイルの全体像
  - 検証結果（実行できなかった検証は、成功と区別して書く）
  - 計画からの差異
  - 各役割に要求したモデルとeffort、そのうち適用を確認できたもの
  - 計画ディレクトリの場所（ユーザーが後から参照できるように）

## 注意事項

- コミット・プッシュはユーザーが依頼した場合のみ行う。
- 途中でタスクのスコープが変わるような発見があった場合は、実装を進める前にユーザーに確認する。実装担当は自分で判断せず、親に戻す。
- 小さすぎるタスク（1ファイル・数行の変更）にこのワークフローを使うのは過剰。その場合はその旨を伝え、直接実装を提案する。
