# impl — Phased Implementation

実装タスクを「計画」と「実装」に分け、計画をフェーズごとの小さなJSONファイルとして一時ディレクトリに書き出してから、フェーズ単位で実装するワークフロー。計画JSONはgitリポジトリには含めない。

計画・実装の実行者は環境に応じて選ぶ:

1. **同梱エージェントがある場合**（Claude Codeプラグインとしてインストールされている場合）: 計画には `phase-planner`、実装には `phase-implementer` エージェントを使う
2. **同梱エージェントは無いがサブエージェント機構がある場合**（Task/Agentツール等）: 計画には読み取り中心のエージェント（Plan / Explore / general-purpose 等）、実装には general-purpose 等を使う
3. **サブエージェント機構が無い場合**: 同じ手順を自分自身で順に実行する

計画JSONのスキーマは `references/plan-schema.md` にある（`LOAD references/plan-schema.md`）。サブエージェントに委譲する場合は、`phase-planner` / `phase-implementer` 以外のエージェントはこのスキーマを知らないため、**スキーマの内容を起動プロンプトに含めること**（同梱エージェントに対しても含めてよい。プロンプトのスキーマが常に優先される）。

## ワークフロー

### Step 0: effortレベルの決定

ユーザーのプロンプトにeffortレベルの指定があるか確認する。

- **指定がある場合**: そのレベル（low / medium / high）を使う。「軽く・ざっくり」→ low、「普通に」→ medium、「徹底的に・入念に」→ high と解釈してよい。
- **指定がない場合**: **必ずユーザーに選択させる**（AskUserQuestion等の選択UIがあればそれを使い、なければ質問して回答を待つ）。勝手にデフォルトを決めない。選択肢:
  - `low` — 最小限の探索と最短の実装。小さな変更向け
  - `medium` — 標準的な探索と実装。影響範囲の確認を含む
  - `high` — 徹底的な探索と実装。エッジケース・テスト追記まで含む

決定したeffortレベルは、以降のすべての工程（サブエージェントを使う場合はその起動プロンプト）に明記して引き継ぐ。

### Step 1: 計画出力ディレクトリの用意

計画JSONは**gitリポジトリの外**に置く。リポジトリ内に作成してはならない。

- 環境が用意する作業用一時ディレクトリ（scratchpad等）があればその下、なければ `/tmp` の下に作る。例: `/tmp/impl/<YYYYMMDD-HHMMSS>/`
- `mkdir -p` で作成し、絶対パスを控えておく。

### Step 2: 計画立案

計画立案は読み取り専用で行う（ソースコードには一切変更を加えない）。上記の実行者選択に従い、サブエージェントを1体起動するか、自分で実行する。指示・実行内容:

1. タスク内容（ユーザーの依頼の全文または忠実な要約）とeffortレベルに応じてコードベースを探索する
2. 変更を依存関係順のフェーズに分割する（例: 型定義 → コアロジック → 呼び出し側 → テスト）。各フェーズは独立して実装・検証できる単位にする
3. フェーズごとに `phase-01.json`, `phase-02.json`, ... を、全体索引を `plan-index.json` を出力ディレクトリ（絶対パスで指定）に書き出す
4. **1ファイルを大きくしすぎない**（目安: 約8KB / ステップ10個以内。超えるならフェーズをさらに分割する）

### Step 3: 計画の確認

1. `plan-index.json` を読み、フェーズ構成と依存関係を把握する。
2. ユーザーにフェーズ一覧（タイトル・目的・依存関係）を簡潔に提示する。
3. 計画に明らかな問題（タスクとの乖離、過剰な分割など）があれば、先へ進む前に修正する。

### Step 4: フェーズごとの実装

フェーズを `dependsOn` の依存関係順に実装する。サブエージェントを使う場合は1フェーズ = 1エージェントで起動する。指示・実行内容:

- 担当する `phase-NN.json`（と `plan-index.json`）を読み込むこと。計画の全文をプロンプトに貼り付けず、ファイルパスを渡して読ませる（コンテキストを小さく保つため）
- effortレベル
- そのフェーズのスコープ内だけを実装すること。計画外のリファクタリングには手を出さない
- 計画と実際のコードが食い違う場合は、フェーズのgoalを達成する範囲で現実に合わせて調整し、報告に明記すること
- `verification` に書かれたコマンド・手順をすべて実行し、通ることを確認すること

依存が互いに独立なフェーズは、変更対象ファイルが重ならない場合に限り並行して進めてよい。

### Step 5: フェーズ間の検証と完了報告

- 各フェーズ完了ごとに結果を確認する。verification失敗や計画からの逸脱があれば、次フェーズに進む前に対処する。
- 全フェーズ完了後、プロジェクトのテスト・リント等の全体検証を実行する。
- 最終報告には以下を含める:
  - 実装されたフェーズと変更ファイルの全体像
  - 検証結果
  - 計画JSONの置き場所（ユーザーが後から参照できるように）

## 注意事項

- コミット・プッシュはユーザーが依頼した場合のみ行う。
- 途中でタスクのスコープが変わるような発見があった場合は、実装を進める前にユーザーに確認する。
- 小さすぎるタスク（1ファイル・数行の変更）にこのワークフローを使うのは過剰。その場合はその旨を伝え、直接実装を提案する。
