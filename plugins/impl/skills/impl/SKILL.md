# impl — Phased Implementation

実装タスクを「計画フェーズ」と「実装フェーズ」に分け、それぞれ専用のサブエージェントに委譲するワークフロー。計画はフェーズごとの小さなJSONファイルとして一時ディレクトリに書き出し、gitリポジトリには含めない。

引数: `$ARGUMENTS` にタスク内容が入る。effort指定（`effort: low` / `effort: medium` / `effort: high`、または「軽く」「徹底的に」等の表現）が含まれることがある。

## ワークフロー

### Step 0: effortレベルの決定

ユーザーのプロンプト（`$ARGUMENTS` および会話の文脈）にeffortレベルの指定があるか確認する。

- **指定がある場合**: そのレベル（low / medium / high）を使う。「軽く・ざっくり」→ low、「普通に」→ medium、「徹底的に・入念に」→ high と解釈してよい。
- **指定がない場合**: **必ず AskUserQuestion ツールでユーザーに選択させる。** 勝手にデフォルトを決めない。選択肢は以下の3つ:
  - `low` — 最小限の探索と最短の実装。小さな変更向け
  - `medium` — 標準的な探索と実装。影響範囲の確認を含む
  - `high` — 徹底的な探索と実装。エッジケース・テスト追記まで含む

決定したeffortレベルは、以降のすべてのサブエージェント起動プロンプトに明記して引き継ぐ。

### Step 1: 計画出力ディレクトリの用意

計画JSONは**gitリポジトリの外**に置く。リポジトリ内に作成してはならない。

- セッションのscratchpadディレクトリがシステムプロンプトに示されている場合はその下、なければ `/tmp` の下に作業ディレクトリを作る:
  - 例: `<scratchpad>/impl/<YYYYMMDD-HHMMSS>/` または `/tmp/impl/<YYYYMMDD-HHMMSS>/`
- `mkdir -p` で作成し、絶対パスを控えておく。

### Step 2: 計画立案サブエージェントの起動

`phase-planner` エージェント（このプラグイン同梱。利用できない環境では Plan / Explore 系の読み取り中心エージェント、それもなければ general-purpose で代替）を **1体** 起動する。プロンプトには必ず以下を含める:

1. タスク内容（ユーザーの依頼の全文または忠実な要約）
2. effortレベルと、そのレベルでの探索の深さ
3. 計画出力ディレクトリの絶対パス
4. 出力形式の指示:
   - フェーズごとに `phase-01.json`, `phase-02.json`, ... として分割して書き出す
   - 全体概要を `plan-index.json` に書き出す
   - **1ファイルを大きくしすぎない**（目安: 約8KB / ステップ10個以内。超えるならフェーズを分割）
   - ソースコードには一切変更を加えない

エージェント定義（`agents/phase-planner.md`）にJSONスキーマの詳細があるため、phase-plannerを使う場合スキーマの再説明は不要。代替エージェントを使う場合は、phase-plannerの定義にあるスキーマをプロンプトに含めること。

### Step 3: 計画の確認

サブエージェント完了後:

1. `plan-index.json` をReadで読み、フェーズ構成と依存関係を把握する。
2. ユーザーにフェーズ一覧（タイトル・目的・依存関係）を簡潔に提示する。
3. 計画に明らかな問題（タスクとの乖離、過剰な分割など）があれば、phase-plannerに追加指示を出して修正させてから先へ進む。

### Step 4: 実装サブエージェントの起動

`phase-implementer` エージェント（このプラグイン同梱。利用できない環境では general-purpose で代替）を起動し、計画JSONをもとに実装させる。

- **依存関係のあるフェーズは順番に**、1フェーズ = 1エージェントで起動する。
- `dependsOn` が互いに独立なフェーズは、変更対象ファイルが重ならない場合に限り並列起動してよい。
- 各エージェントのプロンプトには必ず以下を含める:
  1. 担当する計画JSONファイルの絶対パス（`phase-NN.json`）と `plan-index.json` のパス
  2. effortレベル
  3. 「JSONを読み込み、そのフェーズのスコープ内だけを実装し、verificationを実行して結果を報告する」こと
- 計画の全文をプロンプトに貼り付けない。パスを渡してエージェント自身に読ませる（コンテキストを小さく保つため）。

### Step 5: フェーズ間の検証と完了報告

- 各フェーズ完了ごとに実装エージェントの報告を確認する。verification失敗や計画からの逸脱が報告されたら、次フェーズに進む前に対処する（同じエージェントへの追加指示、または計画の修正）。
- 全フェーズ完了後、プロジェクトのテスト・リント等の全体検証を実行する。
- ユーザーへの最終報告には以下を含める:
  - 実装されたフェーズと変更ファイルの全体像
  - 検証結果
  - 計画JSONの置き場所（ユーザーが後から参照できるように）

## 注意事項

- コミット・プッシュはユーザーが依頼した場合のみ行う。
- 途中でタスクのスコープが変わるような発見があった場合は、実装を進める前にユーザーに確認する。
- 小さすぎるタスク（1ファイル・数行の変更）にこのワークフローを使うのは過剰。その場合はその旨を伝え、直接実装を提案する。
